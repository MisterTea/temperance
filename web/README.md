# Temperance Next.js policy service

This is the canonical web service. It implements the existing `/v1` WireGuard enrollment/device/gateway protocol directly in TypeScript. It does not proxy the old Python service. Python remains the Linux VPN/DNS enforcement plane and the standalone DNS mode; `temperance.control` is retained only for legacy migration/reference tests.

The Next.js App Router serves the family dashboard and authenticated API. Persistent storage uses the documented [libSQL HTTP pipeline](https://docs.turso.tech/sdk/http/reference), with atomic revision compare-and-swap updates. There is no process-memory or temporary-file production fallback. Use a managed Turso database or a self-hosted libSQL server. One deployment manages one household; do not publish it as a shared multi-tenant SaaS without additional account isolation.

## Local development

Requires Node 22+ and Docker for the optional local database:

```sh
docker run --rm --name temperance-libsql -p 127.0.0.1:8081:8080 \
  -v temperance-libsql-data:/var/lib/sqld -e SQLD_NODE=primary \
  ghcr.io/tursodatabase/libsql-server:latest
cd web
npm ci
cp .env.example .env.local
# Fill in independent random secrets, your gateway's public key and endpoint.
npm run dev
```

The named database volume survives container recreation. The local unauthenticated SQL endpoint is loopback-only. Production database URLs require HTTPS and a private database token. The gateway public key is generated by the dedicated Linux gateway; never put its private key in the web service. Native apps intentionally require an HTTPS service origin.

Use `npm run build && npm start` to exercise the standalone production server. The start script copies static assets to the standalone output. Use a reverse proxy for self-hosted HTTPS. The root `deploy/Dockerfile` and Compose recipe now build this Next.js service.

## Vercel

Import `MisterTea/temperance` and set the project root directory to **web**. Next.js is auto-detected; `vercel.json` records the framework. Create/connect a persistent Turso/libSQL database and configure every variable from `.env.example` in Vercel's server-side environment settings. Set `TEMPERANCE_PUBLIC_URL` to the actual stable HTTPS domain. Never prefix secrets with `NEXT_PUBLIC_`.

Build command: `npm run build`. Do not run the Python gateway, VPN, or a local SQLite database in Vercel Functions; they are a separate always-on Linux service. A new process or cold start must read the same SQL database. Verify authentication, enrollment, a policy change reaching the gateway, and data persistence after redeploy before enrolling real devices. Vercel deployments in this repository are configuration/build verified; no account or paid hosting resource is automatically provisioned.

## Cloudflare Workers

The project uses Cloudflare's documented OpenNext adapter with pinned compatible versions: Next.js 16.3.8 and OpenNext 1.20.10. Next.js 16.4 currently changes preview-manifest loading in a way that fails this adapter's runtime; do not upgrade only the framework without running the Worker smoke test. The build includes a patched-safe glob dependency override; `npm audit` is clean for the pinned graph.

```sh
npm ci
npm run cloudflare:build
# Set secrets first through Wrangler's prompted inputs or Cloudflare's dashboard.
npx wrangler secret put TEMPERANCE_ADMIN_TOKEN
npx wrangler secret put TEMPERANCE_GATEWAY_TOKEN
npx wrangler secret put TEMPERANCE_DATABASE_TOKEN
# Configure the remaining server-side values in Cloudflare's dashboard or secrets.
npm run cloudflare:deploy
```

`wrangler.jsonc` enables `nodejs_compat`, static assets, and the adapter's self-reference service binding. Use persistent HTTP/libSQL storage, not a local file or Worker-memory map. For local runtime verification, copy the environment values into a private `.dev.vars` with a localhost origin matching the preview port, run `npm run cloudflare:build`, then `npx wrangler dev --port 3001`. No Cloudflare login is required for local preview. Full-stack deployments target **Workers**, not a static Pages export. `cloudflare:deploy` is a deliberate operator step and is not run automatically by the assistant or CI.

## Tests

```sh
npm run typecheck
npm test
TEMPERANCE_TEST_DATABASE_URL=http://127.0.0.1:8081 npm test
npm run build
npm run cloudflare:build
```

The database test verifies independent instances and concurrent writes against a real HTTP SQL server. Shared policy cases in `specs/policy-cases.json` run in TypeScript and Python. The Linux traffic integration suite verifies actual WireGuard forwarding and policy packet rules. Unit tests alone do not prove parity or physical-client operation; follow `docs/research/circle-feature-audit.md` for remaining work.

## Migrating an existing Temperance instance

Keep the original SQLite database and gateway private key backed up. Export the old control-plane database without modifying it:

```sh
python3 scripts/export_legacy_policy.py data/control.sqlite3 \
  --output /private/path/temperance-migration.json --timezone America/Chicago
```

Configure Next.js with the same VPN endpoint/public key and gateway/admin secrets. Sign in, restore the generated file through Settings, and retain the same HTTPS origin so existing native clients continue to work. Point the gateway's `--service` URL at that origin. If you change the origin, native clients currently need an administrator reset/re-enrollment until the planned origin-migration UI is implemented. VPN peer public keys and device-token hashes are preserved. DNS-only LAN assignments are not converted into fake VPN enrollments; configure the home-routing mode separately when it is implemented. Code expiration and one-use enrollment semantics remain unchanged. Existing clients' enrollment response shape remains compatible.
